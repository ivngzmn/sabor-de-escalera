# Consent and disabled email foundation

Device consent is independent of account autosave. `readConsent()` returns version 1 with optional preferences, recovery and analytics off by default; `updatedAt` is empty until an explicit choice. `updateConsent({preferences,recovery,analytics})` writes only those booleans, version and ISO decision time under `escalera:consent`. No identities or draft text enter consent. Rejected choices persist to avoid repeated prompts. Invalid/old records fail closed. Blocked storage permits only a page-lifetime choice; withdrawal tries to remove any stale stored grant if a replacement write fails. If storage entirely denies writes/removal, the page remains revoked but persistence cannot be guaranteed after reload; future capture integrations must always read current consent before capture.

The shared React banner/settings controls stay disabled until hydration reads the current device choice. Privacy settings remain linked from every shared footer, with English and Spanish purpose copy. Scrolling/Escape/dismissal never grant consent. No preference or recovery payload is implemented here. Task5 must gate local text recovery on `readConsent().recovery`, account-scope recovery keys and clear them on logout/reset/deletion; never store raw images/base64. It must keep account autosave independent of this module.

Optional writers must own keys under `escalera:preferences:`, `escalera:recovery:` or `escalera:analytics:` in local/session storage. Withdrawal revokes the minimal record before callbacks and clears only those prefixes. `registerConsentCleanup(category, stopAndClear)` supplies the narrow lifecycle seam: immediately stop/clear if already off, then stop/clear upon withdrawal and storage events from another tab; return its unsubscribe on component teardown. Cleanup callbacks are isolated so one SDK failure cannot block another category. SDK-private cookies/storage outside these prefixes must be removed by their own callback, never with whole-storage clearing. Task10 must independently verify PostHog free aggregate access and 90-day retention before any capture. Consent or `ANALYTICS_ENABLED=true` alone cannot certify those gates. No analytics SDK is imported or initialized here.

`src/features/notifications/email.ts` re-exports a server-only adapter; client imports fail the build boundary. `sendEmail(record)` produces a result and persists an immutable minimal `EmailRecord` through the PostgreSQL store before delivery. It contains only recipient member ID, notification kind, category, reference and time. Enqueue the durable inbox/request first; an email error must never cause inbox rollback/deletion. Task10 should enqueue inbox and send ledger in its own durable notification transaction where appropriate, then call delivery after commit. No current route calls email delivery. Preferences default off and are separate from browser consent and in-app preferences.

`EMAIL_NOTIFICATIONS_ENABLED=false` and `AUTO_TRANSLATION_ENABLED=false` remain initial configuration. Member email is hard-disabled even if the email flag is set. Independent owner-controlled domain verification, private credentials/from address, free-plan quota proof, signed bounce/complaint webhook verification and inbox/preferences/suspension integration are needed before a reviewed code change can open this gate. No provisioning, live sending or paid service occurs in this task. Clerk sign-in is independent.

The explicit test adapter requires actual `NODE_ENV=test`, a test runtime marker, and exactly Resend's synthetic `delivered@resend.dev` recipient; no production route or flag exposes it. Tests inject provider transport; no live requests occurred. Templates send category/time/reference plus a protected app link, never report/support text or images. Current reference contracts use `/admin?reference=…` or `/notifications?reference=…`; Task10 must implement protected reference routing before member activation.

The ledger deduplicates both send ID and recipient/kind/reference and rejects changed payload reuse. Atomic claims prevent concurrent sends, with maximum five attempts within 23 hours of the first attempt. Provider request uses that stable send ID as `Idempotency-Key`. Sent/suppressed records are terminal. Fresh eligibility queries read member suspension, current verified email, separate preference and address suppression immediately before transport; missing members fail closed. Bounce/complaint processing must authenticate its provider event before calling server-side `suppress(email)`. No public webhook exists yet.

Resend retains idempotency keys for 24 hours, so expired failed attempts and crashed/accepted-but-unrecorded sending states require provider reconciliation instead of automatic takeover/retry. This slice leaves those states durable and does not implement a queue worker, scheduler, webhook or automatic retry loop. Task10 must design replay, signed event handling and reconciliation before activation. Failed transport returns a generic error without provider bodies or private details.

Official Resend contracts checked 2026-10-12: [Send API](https://resend.com/docs/api-reference/emails/send-email), [Idempotency](https://resend.com/docs/dashboard/emails/idempotency-keys), [Synthetic test emails](https://resend.com/docs/dashboard/emails/send-test-emails). These support the prepared request shape/test path; they do not constitute live domain or delivery proof.
